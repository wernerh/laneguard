# Security model

Laneguard is a set of controls around scheduled agents that can change a repository. This page says what each control is, what enforces it outside the model, which test exercises it, and where it stops working. The README's [Security](../README.md#security) section is the short version; the [design spec](design-spec.md) is the long one.

> **Status: pre-alpha.** The guard scripts and their unit tests exist and pass. The controls have **not** been exercised end to end against live GitHub, and no results from live agent runs exist. Several controls rely on repository settings (branch protection, the App's permissions) that Laneguard cannot enforce for you, only check with `doctor`. Treat everything here as a description of intended and unit-tested behaviour, not a track record.

## Three statements to read first

1. **Permission scoping is not a sandbox.** The tool allowlist in `.claude/settings.json` and the GitHub App's scopes limit what the agent is *permitted* to ask for. Anything the project allows to run (your test command, your build) executes arbitrary code with the job's environment, including the Anthropic key and the App token. Run lanes on ephemeral runners or containers if that matters. `guard/allowlist.py` says the same in its docstring.
2. **The reviewer's verdict is posted by the lane's own token.** `laneguard-review` is written by `forge.py` using the same installation token the lane uses, so GitHub cannot tell the reviewer from the lane. The independence is **model and context separation** (a read-only subagent with a fresh context, by default a different model, that sees only the diff, the validation output and the plan's acceptance criteria), not identity separation. It is a useful second opinion, not an authenticated one. Configuring the same model for implementer and reviewer weakens it, and `doctor` only warns about that.
3. **Prompts are not enforcement.** Agent files state intent. The mechanisms below are the enforcement. Where a row says "instruction only", that control depends on the model following its instructions and should be treated accordingly.

## Threat model

| Threat | Mechanism (what enforces it) | Tests that cover it | Residual risk |
|---|---|---|---|
| **Prompt injection through issues, PRs or comments** | `forge.py trust` only treats an issue as actionable when its author is an owner or triage-level collaborator, or an owner applied `laneguard-ready` (and the label is not later removed); all user text is returned under `untrusted_` keys, truncated and scanned for injection phrases (`scan_untrusted`); acceptance criteria come from the approved plan, not issue text. The triager, implementer and reviewers are specified never to see raw text (**instruction only**: the agents are told this, and nothing in code stops an orchestrator from passing raw text on) | `guard/tests/test_forge.py`: `test_owner_created`, `test_triage_collaborator_created`, `test_read_only_collaborator_not_trusted`, `test_stranger_not_trusted`, `test_ready_label_by_*`, `test_flags`, `test_read_issue_marks_user_text_untrusted_and_truncates`; `evals/tests/test_offline.py`: `InjectionCorpusScan` over `evals/corpus/injection/` | The phrase scan is a heuristic. It folds NFKC and common confusables (so the corpus's Cyrillic homoglyph item is flagged), but a pure paraphrase with no trigger phrase cannot be caught. The corpus is exercised against this scanner only; whether the agents resist the same texts is not yet tested. A model can still be steered by hostile content inside code or docs it legitimately reads. The structural controls (protected paths, allowlist, review, branch protection) must hold even when the scan misses |
| **A lane edits its own rules** (protocol, config, guard scripts, workflows, allowlist, pin) | Protected paths: CODEOWNERS routes them to owners; `check.py` fails any PR touching them unless authored by an owner login, using the config from the **base** commit, run from a copy of `check.py` taken from the base commit; `allowlist.py` denies `Edit`/`Write` on every protected path; the App has no workflow-write permission; the bot is never an owner | `test_check.py`: `test_non_owner_edit_of_each_protected_path_fails`, `test_config_is_read_from_base_so_a_pr_cannot_make_itself_an_owner`, `test_bot_with_an_owner_name_is_not_an_owner`, `test_moving_a_protected_file_away_is_caught`; `test_allowlist.py`: `test_every_protected_path_is_denied_for_edit_and_write`; `test_doctor.py`: `test_tampered_guard_script_fails`, `test_loosened_allowlist_fails`; `evals/tests`: `CheckProtectedPaths` | Only works if branch protection requires the check and CODEOWNERS review. An owner who approves a malicious PR defeats it. The allowlist is not a sandbox (statement 1) |
| **Weakened tests, lint or CI "to make it pass"** | `check.py` flags disabled or deleted tests, net removal of test cases, lowered or removed thresholds, `--no-verify` and skip markers, CI steps made non-blocking or removed, blanket lint suppressions, and edits to branch-protection config. For non-owner PRs these are errors; for owners they are warnings | `test_check.py`: `test_disabled_test_python`, `test_disabled_test_js`, `test_deleted_test_file`, `test_net_removal_of_test_cases`, `test_threshold_lowered`, `test_bypass_flags`, `test_ci_made_non_blocking`, `test_ci_step_removed`, `test_blanket_lint_suppression`, `test_branch_protection_config_edit`; `evals/tests`: `CheckWeakenedChecks` | Pattern matching on diffs. The skip markers include the conditional forms (`skipIf`, `skipUnless`, `skipif`), but emptying a test's assertions without removing the test is not detected. The independent reviewer is the second line, and it is a model |
| **Lock races, double runs, crashed runs** | `lock.py` is the only code that touches `refs/laneguard/lock`; every change is a compare-and-swap push with an explicit expected old value, so the server accepts only one of two racers; stale takeover requires the stale SHA; time comes from the forge's `Date` header, not the local clock. `check.py` alarms when a lock is older than 2 x TTL | `test_lock.py`: `test_n_parallel_acquirers_exactly_one_wins`, `test_n_parallel_takeovers_of_a_stale_lock_exactly_one_wins`, `test_stale_takeover_is_logged_and_old_holder_loses`, `test_takeover_loses_cleanly_to_a_late_heartbeat`, `test_heartbeats_keep_a_long_run_alive`, `test_corrupt_lock_is_never_taken_over`, `test_no_wall_clock_is_read_by_lock_py`, `test_two_runs_with_wildly_different_local_clocks_agree`; `test_check.py`: `test_stale_lock_alarm_fails` | The tests run against local git remotes, not GitHub, so GitHub-specific behaviour (for example ref-update rules) is untested. A token with contents write can write any ref; the lock is protected by code and the allowlist (which denies `git update-ref` and force pushes), not by a server rule. A GitHub outage stalls lanes (fails safe: nothing runs) |
| **Forged or replayed approvals** | `forge.py approvals` accepts `/approve <gate>` only from a listed owner, with a human author association (`OWNER`, `MEMBER`, `COLLABORATOR`), never from a bot, never edited after posting, as the whole first line of the comment, for the right gate; PR merge approvals must be on the current head and a later "changes requested" supersedes. Email is never an input | `test_forge.py`: `test_valid_owner_approval`, `test_not_an_owner`, `test_bot_cannot_approve_even_if_named_as_owner`, `test_edited_comment_is_rejected`, `test_wrong_gate_is_ignored`, `test_trailing_text_on_the_first_line_does_not_count`, `test_quoted_or_embedded_approve_does_not_count`, `test_association_must_be_human_role`, `test_two_approvals_required`, `test_pr_merge_gate_accepts_review_on_current_head_only`, `test_later_changes_requested_supersedes_approval` | Compromise of an owner's GitHub account. Checks run against API responses the tests fake; real GitHub payloads may differ in ways not yet seen. Gate enforcement beyond code (for example, the lane choosing not to proceed) is instruction only |
| **Runaway cost or loops** | Mechanical: the workflow's `timeout-minutes` and `--max-turns`; `history.py` computes the circuit breaker from recorded runs (N consecutive failures, M on one PR) and pauses the lane, and compares the month's recorded cost to `monthly_cost_ceiling_usd`; a lane can only create `PAUSED*` flags, and unpause refuses non-owners | `test_history.py`: `test_consecutive_failures_trip`, `test_same_pr_failures_trip_but_other_prs_do_not`, `test_breaker_trips_pause_and_cannot_be_reset_by_new_runs`, `test_cost_ceiling_uses_current_month_only`, `test_pause_and_owner_only_unpause`, `test_pause_check_exit_codes_and_record`; `test_doctor.py`: `test_timeout_must_match_config`, `test_max_turns_must_match_config` | `budgets.per_run.max_tokens`, `max_open_prs_per_lane` and `max_issues_created_per_day` are **instruction only** today: they appear in the config and the lane skill but no script enforces them. Cost in `runs.jsonl` is reported by the lane's own run, so the monthly ceiling is only as accurate as that report; set a spend limit on the Anthropic key itself as the real backstop. `--max-turns` is rendered from `budgets.per_run.max_turns` by `init` and `doctor` fails when the workflow and config differ |
| **Secret leakage** (commits, logs, reports) | `check.py` scans added lines for secret patterns and fails even for owners, never printing the value; `history.py` redacts secret shapes and environment values from records before writing; the allowlist denies reading `.env`, `~/.ssh`, `~/.aws`, etc. and `env`/`printenv`; the App has no secrets permission | `test_check.py`: `test_each_pattern_fails_and_never_prints_the_value`, `test_secrets_fail_even_for_owners`, `test_the_repo_itself_contains_no_secret_patterns`; `test_history.py`: `test_secret_shapes_and_env_values_are_redacted`, `test_secrets_are_scrubbed_before_writing`; `test_allowlist.py`: `test_force_push_network_cloud_and_secrets_denied` | Pattern-based: a secret in an unrecognised shape passes. Allowlist rules do not stop code the project runs from reading the environment (statement 1). The job holds the Anthropic key and App token by design |
| **Over-privileged identity** | The App is created with only contents, pull requests, issues and commit statuses; `doctor --as lane` fails when the lane's token is an owner's, or reports admin or maintain rights; `init` and `doctor` refuse a bot in `owners:` | `test_doctor.py`: `test_good_lane_identity_and_rules_pass`, `test_owner_token_used_by_lane_fails`, `test_admin_lane_token_fails`, `test_bot_owner_fails`, `test_app_bypass_fails_and_user_bypass_warns` | `doctor` cannot see an App's permission list, only what the API reports for the token's repository permissions; if GitHub does not return them the check is skipped. You must create the App correctly |
| **Merging without an owner or without the checks** | Branch protection or ruleset on the default branch (required PR, code-owner review, `laneguard-guard / check`, plus `laneguard-review` for autonomous lanes, no bypass for the App). Laneguard cannot set this; `doctor` reads it | `test_doctor.py`: `test_rules_each_missing_guarantee_fails`, `test_classic_protection_is_understood`, `test_autonomous_requires_review_check`, `test_app_bypass_fails_and_user_bypass_warns`, `test_unreadable_rules_skip` | These tests feed `doctor` synthetic API data. A mistake in the real setup, or in how `doctor` reads real responses, is exactly what an end-to-end run would find. See [branch protection](setup/branch-protection.md) |
| **Malicious or surprise engine update** | The engine is pinned to a full 40-character commit SHA in a protected file; `check.py` and `doctor` reject a short or missing pin; the lane workflow checks out the engine at that SHA; workflows' third-party actions must be pinned to full SHAs (`doctor`) | `test_check.py`: `test_pin_must_be_a_full_sha`, `test_missing_pin_fails`; `test_doctor.py`: `test_short_pin_fails`, `test_unpinned_action_fails`, `test_pull_request_target_fails` | You still trust the commit you pin and the pinned actions. `migrate` only ever produces a PR for owner review and never touches files you edited |

## What is verified, and how

`doctor` turns the table above into runnable checks (config, owners, engine pin, hashes of the guard scripts, CODEOWNERS coverage, the tool allowlist, workflow hygiene, model separation, reviewer agents, token identity, branch protection). It stores nothing, so there is no "passed" marker for a lane to forge; lanes specified to run it with `--strict --as lane` before an `autonomous` run. See [branch protection](setup/branch-protection.md#what-doctor-verifies) for the exact check ids.

`evals/` holds an injection corpus, fixture repositories and a scorer. Its offline tests measure the mechanical guard only. They do **not** measure how a model behaves; that needs live runs, and none have been published.

## Known limits

Read these before enabling `autonomous` mode.

- **Not a sandbox.** See statement 1. Allowlisted commands run real code with the job's secrets.
- **Reviewer verdict is not identity-independent.** See statement 2. The status is posted by the lane's token. A compromised lane process could in principle post `APPROVE` itself, because the status API accepts it from the same token. The defence is that the reviewer is a separate model and context, and that the verdict is one of several controls, not that GitHub can attest who wrote it.
- **Instruction-only controls.** The triager firewall (nothing in code stops raw text being passed on), the gatekeeper's gate decisions, the rule that a lane does one major task, the PR and issue caps, `max_tokens` and the "refuse to run without a passing `doctor`" step are carried by prompts and skills. Their agent files are protected paths and the evals check their structure, but a model can still misbehave.
- **"Read-only" agents are read-only by instruction where Bash is concerned.** The observer, triager and validator have Bash so they can read the forge and (for the validator) run the configured validation commands. They are told to use only `forge_read.py`, a wrapper that exposes the read commands and whose Forge has its write path closed in code; `evals/conformance/check_agents.py` fails any read-only agent whose prompt points at `forge.py`. But the project allowlist in `.claude/settings.json` cannot distinguish subagents, so `python3 .laneguard/guard/forge.py:*` (which the orchestrator needs for claims, PRs, the review status and merges) is callable by every subagent in the run. What stops a read-only agent from writing is therefore its prompt, the conformance check, `forge.py`'s own write allow-list (this repository's issues, PRs, labels, comments and the review status only) and branch protection, not the `tools:` line. The two scripts are distinct on purpose, so a `forge.py write` from a read-only step is visible in the run log and can be denied by a hook. See [issue #6](https://github.com/wernerh/laneguard/issues/6).
- **Heuristic detectors.** Injection phrase scanning, secret patterns and weakened-test detection are pattern matches. Known limits are listed in the table and asserted as documented limits in `evals/tests/test_offline.py`.
- **`doctor` reads, it does not enforce.** It checks what the API reports. It cannot see settings it has no permission to read (it then reports SKIP), cannot confirm who actually holds admin on the repository, and checks the default branch only (not `laneguard-data`).
- **The lock and history are git state.** `refs/laneguard/lock` and the `laneguard-data` branch can be written by anything holding the bot's contents-write token. Branch rulesets can stop deletion and force-push of `laneguard-data` but not an ordinary commit that removes a pause flag, and they do not cover the lock ref. Owner-only unpause is enforced by `history.py` and the allowlist, not by GitHub.
- **Cost accounting is self-reported.** See the runaway-cost row. Use a provider-side spend limit.
- **Tested against fakes and local git.** The unit tests use injected transports and local bare repositories. They do not prove behaviour against GitHub's real API, rate limits, or Actions runners.
- **Scaffolded CODEOWNERS is broad.** The template owns `*`, so with code-owner review required a lane cannot merge its own PR even in `autonomous` mode until you narrow it. Safe by default, but surprising.
- **Solo owners need a bypass.** GitHub does not let an author approve their own PR, so a one-owner project usually adds that owner as a bypass actor, which `doctor` reports as a warning.
- **Compromised owner accounts and malicious approvals** are out of scope. So is anything the agent's environment can reach outside the repository.
- **The required-check name is unconfirmed against live GitHub.** See [branch protection](setup/branch-protection.md#confirm-the-check-name).
